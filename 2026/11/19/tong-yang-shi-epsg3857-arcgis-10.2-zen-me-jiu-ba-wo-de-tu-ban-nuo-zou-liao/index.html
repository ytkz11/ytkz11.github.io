同样是 EPSG3857，ArcGIS 10.2 怎么就把我的图斑挪走了？

2026年11月19日遥感

最近在处理遥感影像的矢量成果时，碰到了一个挺离谱的问题。

输入是一景 TIF 影像，输出是经过一系列后处理得到的 SHP 矢量文件。按理说，影像和矢量使用同一个坐标系，叠加起来应该严丝合缝。

结果偏偏出了问题。

在 QGIS 里检查，坐标系识别正常。换到 ArcGIS 10.2，尤其是经过重新投影等操作之后，图斑的位置就不对了。

更奇怪的是，查看坐标系信息，明明都是 EPSG:3857。

同一个坐标系，换个软件，怎么还能把位置搞错？

最开始以为是代码的问题。

是不是栅格转矢量的时候把坐标弄反了？

是不是影像的 Y 轴翻转了？

还是某个处理中间环节丢失了投影信息？

排查了一圈，最后把注意力放到了一个平时不怎么起眼的文件上：

.prj

做 GIS 开发的应该都见过 Shapefile 的这几个文件：

  • .shp：存储几何图形。
  • .shx：几何索引。
  • .dbf：存储属性数据。
  • .prj：记录坐标参考系统。

前三个比较好理解，第四个经常被忽略。我第一次熟悉它们是在几年前在学GEE的时候，想上传矢量到GEE需要把这几个文件上传，缺一不可，多一个也不可（点名shx文件）。

很多时候，我们写完 SHP 文件，确认有个 .prj，软件里能显示出 EPSG 编号，就认为坐标系肯定没问题了。

实际上还真不能这么判断。

PRJ 文件通常使用 WKT（Well-Known Text）描述坐标参考系统。

简单理解，EPSG 编号相当于坐标系的身份证号，WKT 则是坐标系的详细说明书。

比如 EPSG:3857，也就是我们经常说的 Web Mercator（网络墨卡托）投影。

在 Python 里可以这样获取：

from pyproj import CRS

crs = CRS.from_epsg(3857)

print(crs.name)
print(crs.to_epsg())

输出：

WGS 84 / Pseudo-Mercator
3857

看起来没什么问题。

但如果让 pyproj 把这个坐标系转换成 WKT，就有意思了。

print(crs.to_wkt(version="WKT1_ESRI"))

print(crs.to_wkt(version="WKT1_GDAL"))

print(crs.to_wkt(version="WKT2_2019"))

同一个 EPSG:3857，居然可以生成三种不同形式的 WKT。

这也是这次排查的切入点。

先看 WKT1_ESRI。

它生成的内容以这样的形式开头：

PROJCS[
  "WGS_1984_Web_Mercator_Auxiliary_Sphere",
  ...
  PROJECTION["Mercator_Auxiliary_Sphere"],
  ...
]

再看 WKT1_GDAL：

PROJCS[
  "WGS 84 / Pseudo-Mercator",
  ...
  PROJECTION["Mercator_1SP"],
  ...
  AUTHORITY["EPSG","3857"]
]

最后是 WKT2_2019：

PROJCRS[
  "WGS 84 / Pseudo-Mercator",
  ...
  CONVERSION[
    "Popular Visualisation Pseudo-Mercator",
    ...
  ],
  ...
  ID["EPSG",3857]
]

是不是有点奇怪？

同样是 EPSG:3857，第一种叫 Mercator_Auxiliary_Sphere，第二种叫 Mercator_1SP，第三种又成了 Popular Visualisation Pseudo-Mercator。

这不是简单地把坐标系名称改了改。

不同 WKT 版本在投影方法、参数组织、坐标轴描述等方面，都可能采用不同的表达方式。

尤其是 WKT1_ESRI 与 WKT1_GDAL，虽然都属于 WKT1，但使用了不同的软件约定。

现代 pyproj 可以把上述三种定义还原为 EPSG:3857。

问题是，我们的数据不一定只在现代 pyproj 中使用。

有些项目还在用 ArcGIS 10.2，有些使用 QGIS，也有些用 GDAL、GeoPandas、ArcPy 交替处理数据。

写文件的软件能正确理解一个投影定义，不代表另一个软件在所有操作中都能按相同方式处理。

特别是碰到老版本 GIS 软件时，还是要多留个心眼。

这次测试中，我发现一个现象：

使用 pyproj 生成的WKT1_ESRI，QGIS 可以正常识别；但在我使用的 ArcGIS 10.2 工作流程中，重新转换坐标后，结果出现了位置偏移。

随后换成WKT1_GDAL，在当前测试流程中的表现反而正常了。

这就很有意思了。

按名称理解，WKT1_ESRI 应该更适合 ArcGIS 才对。

不过这里需要说明，ArcGIS 本身是支持 ESRI 风格 WKT 的。甚至 Esri 官方给出的 Web Mercator 示例，就使用了 WGS_1984_Web_Mercator_Auxiliary_Sphere 和 Mercator_Auxiliary_Sphere 这样的定义。

因此，不能仅凭这次现象就认为 ArcGIS 10.2 不支持 WKT1_ESRI。

更准确的说法是：

在我这次 ArcGIS 10.2、pyproj 和 SHP 数据的组合中，不同 WKT 写法表现出了兼容性差异。

具体是旧版本对某些定义的解析差异，还是数据转换流程中的其他问题，还需要继续对照实际坐标值验证。

但这次问题至少提醒了我一件事：

不能只看 EPSG 编号，还要关注数据究竟是怎样描述这个坐标系的。

顺着这个问题继续排查，很容易发现另一个常见错误。

假设一份 SHP 的真实坐标是 EPSG:3857。

某个点的坐标可能是：

X = 12957600
Y = 4800000

单位是米。

如果把它真正转换成 EPSG:4326，经纬度大致会变成：

经度 = 116.4001
纬度 = 39.5447

这两个结果描述的是同一个位置，只是坐标表达方式不同。

但如果你不转换坐标，只把 .prj 文件从 EPSG:3857 改成 EPSG:4326，会发生什么？

相当于告诉 GIS 软件：

这组以米表示的坐标，现在是经纬度。

软件当然没办法正确定位。

这就涉及两个经常被混淆的操作：

Define Projection（定义投影）：告诉软件，现有坐标值属于哪个坐标参考系统，不修改几何坐标。

Project（投影转换）：根据原始和目标坐标参考系统，真正计算新的坐标值。

在 GeoPandas 里同样如此。

# 只修改坐标系定义，不转换几何坐标
gdf = gdf.set_crs(
    "EPSG:3857",
    allow_override=True
)

# 真正转换坐标
gdf = gdf.to_crs("EPSG:4326")

这两段代码完全不是一回事。

而且 set_crs() 的前提是，你已经确认数据的实际坐标就是这个坐标系。不能看到图斑错位，就随便换一个 EPSG 编号试试。

在遥感数据处理中，尤其是栅格矢量化、分块处理、空间叠加、多轮坐标转换这些操作，坐标系一旦在中间环节弄错，后面再怎么修 PRJ 都没用。

针对这次问题，我写了个简单的脚本，把几种 WKT 都输出出来。

from pathlib import Path
from pyproj import CRS

crs = CRS.from_epsg(3857)

formats = {
    "WKT1_ESRI": "3857_esri.prj",
    "WKT1_GDAL": "3857_gdal.prj",
    "WKT2_2019": "3857_wkt2.prj"
}

for fmt, filename in formats.items():
    wkt = crs.to_wkt(version=fmt)

    Path(filename).write_text(
        wkt,
        encoding="utf-8"
    )

    parsed = CRS.from_wkt(wkt)

    print(
        fmt,
        "识别EPSG:",
        parsed.to_epsg()
    )

注意，这里只是生成三种投影定义文件，用于比较与测试。它们并没有完成任何坐标转换。

如果确实需要给一个 EPSG:3857 的 SHP 生成 GDAL 风格的 PRJ，可以这样写：

from pathlib import Path
from pyproj import CRS

crs = CRS.from_epsg(3857)

wkt = crs.to_wkt(
    version="WKT1_GDAL"
)

Path("result.prj").write_text(
    wkt,
    encoding="utf-8"
)

前提是 result.shp 中存储的几何坐标本身就是 EPSG:3857。

如果不是，就不能只靠替换 PRJ 解决。

经过这次折腾，我现在处理跨软件的遥感矢量成果，会多检查几项：

  1. TIF 和 SHP 的真实坐标参考系统是否一致。
  2. SHP 的坐标范围是否合理，是否发生过多余的 to_crs() 转换。
  3. .prj 文件里的投影方法及参数，是否被目标软件正确识别。
  4. 在 ArcGIS 中重新投影后，选取一个已知点，对比转换前后的实际坐标。

对于我现在使用的 ArcGIS 10.2 工作环境，WKT1_GDAL 已经表现出了更好的兼容性，因此可以优先作为当前项目的输出方案。

但如果是专门交付 ArcGIS 数据，我仍然建议优先采用 ArcGIS 自带的标准坐标系定义，并用实际坐标验证。

对于其他版本的软件，也没必要一律强制使用 WKT1_GDAL。

毕竟兼容性这个东西，不能光看名字，更不能只看一次测试。

后面我删除了错误的prj，虽然拖到arcgis会提示警告，但是acrgis不会错误坐标转换。

最后还是回到我之前的代码中，优先保存WKT1_GDAL格式的prj文件。

做遥感开发，时间长了就会发现，有些问题真不是算法造成的。

模型推理正常，图斑提取正常，矢量拓扑也没毛病，最后却在坐标系上翻了车。

尤其是 Python 和 ArcGIS 混合开发时，pyproj、GDAL、GeoPandas、ArcPy 各自有自己的版本和处理习惯。我习惯用arcgis作为显示。

同样一个 EPSG 编号，不同软件可能采用不同的 WKT 表达方式；同样一个 PRJ 文件，也需要确认软件是否把它正确理解成了预期的坐标参考系统。

当然，PRJ 不是万能背锅侠。图斑偏移也可能来自错误的 CRS 赋值、重复投影、坐标轴顺序、栅格地理变换参数等问题。

这次折腾最大的收获，不是发现哪一种 WKT 最好，而是以后再看到图层位置不对，知道应该先从哪里查起。

坐标系显示一致，只是第一步。坐标值和投影定义都正确，才是真的对齐。

不然，图斑跑到哪里去了，还得靠猜。

还有，其实我是技术主播。
